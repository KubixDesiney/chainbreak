What the AWS report found

In one eu-west-3 account, a two-hop IAM role chain was given a session policy intended to narrow an agent's authority. It did narrow — but the middle agent still returned ALLOWED for keyvalue.write and objectstore.list in every trial, because those capabilities came from the role's own permission policy rather than the delegated scope. The session policy never granted them and never took them away.

CHAINBREAK reports that as AUTHORITY_EXPANSION at REVIEW severity, with the observation and the interpretation kept in separate fields, and it declines to score the three categories the scenario never exercised.

How this site was verified

Publishing evidence is how accounts leak. Every file here — each page, and each archive attached to the release — was scanned before publication by scripts/verify_public_site_scrub.py, which imports the same compiled patterns chainbreak evidence export --public uses (EVIDENCE_SCHEMA.md section 11) and applies them to HTML, Markdown and every member of every .tar.gz — including the HTML-entity-decoded text, so an identifier cannot hide behind an escape. Residual account IDs, ARNs, hostnames, live namespaces, session names, policy documents and credential-shaped blobs: zero.

The gate is not decorative. It caught a live benchmark namespace in an archive that had been committed as “scrubbed” a day before namespace scrubbing was added to the exporter; that archive was re-scrubbed before anything was published.

Run it yourself, without an AWS account

The scrubbed evidence archives are attached to the v0.1.0 release. Download one and analyse it:

pip install "chainbreak[report]"
tar -xzf aws-m17-valid-block01-scrubbed-sample.tar.gz
chainbreak analyze 01M0A5WS8Q912NJSP0FEH1DWSK \
  --runs-root 01M0A5WS8Q912NJSP0FEH1DWSK --allow-unsealed
chainbreak report 01M0A5WS8Q912NJSP0FEH1DWSK \
  --runs-root 01M0A5WS8Q912NJSP0FEH1DWSK --allow-unsealed --format terminal

--allow-unsealed is required and is not a defect: scrubbing rewrites artifacts after the bundle was sealed, so a published bundle's integrity root no longer matches its own bytes. CHAINBREAK keeps the original root rather than re-sealing over the scrub, and stamps every finding derived from it bundle_root_verified: false — visible in the header of both reports above.

Or generate a fresh apparatus bundle with no download at all:

chainbreak run scenarios/scope-attenuation/basic.yaml --provider fake --seed 1729
chainbreak analyze <run-id>
chainbreak report <run-id> --format terminal
